# Инструкции для агентов

## Синхронизация AGENTS.md и CLAUDE.md

[AGENTS.md](AGENTS.md) и [CLAUDE.md](CLAUDE.md) в корне репозитория — две одинаковые копии общих инструкций для всех агентов. Их содержимое должно совпадать побайтово.

- Перед изменением инструкций прочитай оба файла. Если они разошлись, объедини актуальные сведения из обеих версий, сверяя противоречия с кодом и указаниями пользователя; не теряй дополнения другого агента при копировании.
- Любое изменение правил, каталога окон, описаний возможностей или команд проверки вноси в оба файла в рамках одной задачи. Не веди отдельную историю для Codex или Claude.
- После редактирования перенеси итоговое содержимое в парный файл и проверь совпадение: `git diff --no-index -- AGENTS.md CLAUDE.md` (без вывода, код возврата 0).

## Главный приоритет: только WPF

Актуальная и единственная активно развиваемая версия проекта — **WPF-версия** в каталоге `FractalExplorerWPF/`.

Если пользователь не указал технологию или версию явно, всегда считай, что задача относится к WPF. Ищи, анализируй, изменяй, собирай и проверяй код только WPF-версии.

Каталог `FractalExplorer/` содержит устаревшую **WinForms-версию**. Она заморожена и больше не обновляется.

- Не вноси изменения в WinForms-версию по умолчанию.
- Не дублируй в нее исправления и новые возможности из WPF.
- Не используй ее solution или project для сборки и проверки обычных задач.
- Не выбирай WinForms только потому, что там уже существует похожая реализация.
- Использовать WinForms-код как справочный материал можно только при необходимости; итоговая реализация все равно должна находиться в WPF-проекте.
- Работать с `FractalExplorer/` разрешено только тогда, когда пользователь прямо и однозначно попросил изменить именно WinForms-версию.

При любом неоднозначном запросе выбирай WPF без дополнительного уточнения и кратко указывай это допущение в результате работы.

## Расположение актуального проекта

- Решение: `FractalExplorerWPF/FractalExplorerWPF/FractalExplorerWPF.slnx`
- Проект: `FractalExplorerWPF/FractalExplorerWPF/FractalExplorerWPF/FractalExplorerWPF.csproj`
- Исходный код: `FractalExplorerWPF/FractalExplorerWPF/FractalExplorerWPF/`
- Точка входа и ресурсы приложения: `App.xaml`, `App.xaml.cs`
- Главное окно: `MainWindow.xaml`, `MainWindow.xaml.cs`

WPF-проект использует `net10.0-windows`, nullable reference types и implicit usings. В `.csproj` присутствует framework reference на `Microsoft.WindowsDesktop.App.WindowsForms` для ограниченной совместимости с Windows API/компонентами; эта ссылка не меняет приоритет проекта и не означает, что legacy WinForms-версию нужно обновлять.

Единственная внешняя зависимость — NuGet-пакеты `Vortice.Direct3D11`, `Vortice.DXGI` и `Vortice.D3DCompiler` (тонкие обёртки над Direct3D 11, вместе с `Vortice.Mathematics` и `SharpGen.Runtime` — около 1.2 МБ управляемых сборок, нативных библиотек с собой не несут). Их использует `Core/Rendering3D/` для трёхмерных режимов и вычислительных шейдеров узоров Тьюринга и Gray–Scott; у двумерных Тьюринга и Gray–Scott можно выбрать ЦП без видеокарты. Жюлиа, горящий корабль Жюлиа и их карта выбора C автоматически используют ГП на малом зуме с возвратом на ЦП; остальные двумерные режимы считаются на ЦП. Трёхмерные режимы, включая моделирование Gray–Scott 3D и узоров Тьюринга 3D, считаются только на видеокарте; общее устройство окна — `Core/Rendering3D/Direct3DDeviceHost.cs`.

## Структура WPF-проекта

```text
FractalExplorerWPF/FractalExplorerWPF/FractalExplorerWPF/
├── App.xaml, App.xaml.cs          # запуск и ресурсы приложения
├── MainWindow.xaml, .xaml.cs      # каталог и главное окно
├── Views/                         # окна фракталов, редакторы и диалоги
├── Controls/                      # переиспользуемые WPF-контролы
├── Core/
│   ├── Math/                      # комплексная арифметика и парсеры выражений
│   ├── Rendering/                 # движки, рендереры и растровая инфраструктура
│   └── Rendering3D/               # GPU-рендер и вычислительные шейдеры (Direct3D 11)
├── Models/                        # модели UI, параметров, палитр и сохранений
├── Infrastructure/
│   ├── ColorPicking/              # выбор цвета и экранная пипетка
│   ├── Migrations/                # версии данных, миграции, перенос старой папки Saves
│   └── Serialization/             # JSON-конвертеры
│                                  # также хранилища, настройки, экспорт и сервисы
├── Theming/                       # темы, стили и их хранение
├── Assets/                        # иконки, превью и изображения
└── Properties/                    # настройки проекта и ресурсов
```

Основные границы ответственности:

- Разметка и визуальное состояние окон относятся к `Views/` и XAML.
- Общие элементы интерфейса относятся к `Controls/`.
- Математика и вычислительный рендеринг не должны зависеть от UI и относятся к `Core/`; расчёт кадра на видеокарте — к `Core/Rendering3D/`.
- DTO, состояния и параметры относятся к `Models/`.
- Сериализация, файловые хранилища, настройки и интеграция с ОС относятся к `Infrastructure/`.
- Общие ресурсы оформления относятся к `Theming/` и `Assets/`.

При добавлении любого нового GPU/3D-режима или варианта шейдера включай его в общий дисковый кэш `Infrastructure/ShaderBytecodeCache.cs` через `AppPaths.ShaderCacheDirectory`. Ключ кэша должен учитывать исходник, точку входа и профиль компиляции; при изменении флагов или способа компиляции повышай версию сигнатуры кэша. Новый вариант должен участвовать в команде «Пересобрать шейдеры» на главной странице. Не храни скомпилированный байткод рядом с exe и не вводи отдельную папку кэша для каждого фрактала.

Экспорт текущего снимка, общий облачный менеджер. Четырнадцать вычислительных вариантов, включая реакции и размерные шейдеры размытия, участвуют в общем кэше и пересборке. Связаны Models/TuringModels.cs, Core/Rendering/ITuringEngine.cs, TuringSimulation.cs, TuringRenderer.cs, Core/Rendering3D/TuringGpuEngine.cs, TuringComputeShader.cs, Infrastructure/TuringSaveStore.cs и Serialization/CompressedFloatArrayJsonConverter.cs; подробности — FractalExplorerWPF/TURING_PATTERNS.md. ## Пользовательские данные, сохранения и миграции

Все данные пользователя лежат в `%LOCALAPPDATA%\Fractal Explorer Studio` (`Infrastructure/AppPaths.cs`), а не рядом с exe. Папку открывает кнопка «Открыть папку с данными» в панели «Настройки» главного окна.

```text
Saves\<режим>\<имя>.json + <имя>.png   # по файлу на сохранение, превью рядом с ним
PointsOfInterest\<режим>\<имя>.png     # превью встроенных точек интереса (кэш)
Palettes\  Themes\  Settings\  Logs\   # палитры, темы, настройки, журнал ошибок
shadercache\                           # кэш байткода всех GPU-шейдеров Direct3D
Backups\                               # копии файлов, изменённых миграциями
data-version.json                      # достигнутая версия каталога данных
```

Правила:

- Путь к любому пользовательскому файлу — только через `AppPaths` (`GetSavesDirectory`, `GetPaletteFile`, `GetThemeFile`, `GetSettingsFile`, `EnsureDirectoryFor`). Не писать в `AppContext.BaseDirectory`.
- Байткод GPU-шейдеров хранится в `shadercache\` через `AppPaths.GetShaderCacheFile`; кнопка «Пересобрать шейдеры» в настройках главного окна пересоздаёт общий кэш всех GPU-режимов, включая узоры Тьюринга и Gray–Scott. Другие пользовательские данные при этом не удалять.
- Сохранения режима — наследник `FractalSaveStore<TState>` (`Infrastructure/FractalSaveStore.cs`, классы `*SaveStore.cs`). Категория — имя каталога в `Saves\`; переименовывать её можно только вместе с миграцией.
- **Удаляемые и заменяемые сохранения и превью не стираются бесследно, а уходят в Корзину Windows** через `Infrastructure/RecycleBin.cs`: удаление записи, перезапись под тем же именем, пересчёт превью. `File.Delete` для них не использовать — только для собственных временных файлов.
- `RecycleBin.ReplaceWith` атомарно заменяет файл с резервной копией `<имя>.<идентификатор>.bak`, затем отправляет копию в Корзину. Отказ Корзины вызывает откат; при отказе самого отката `.bak` остаётся рядом, путь указан в исключении и журнале. Не удалять такие копии как временный мусор. Заменённая версия восстанавливается из Корзины под резервным именем.
- `MandelbrotPaletteManager` (также Nova и Коллатц) после ошибки загрузки блокирует запись пользовательской библиотеки и сообщает причину в редакторе; применение к изображению без записи доступно. Палитры записываются через временный файл с атомарной заменой. Не снимать блокировку путём сохранения неполного списка поверх повреждённого файла.
- Изменение формата отдельного сохранения (переименование или перенос свойства, смена единиц) — `SaveFormatUpgrade` в конец списка в `Infrastructure/Migrations/SaveFormat.cs`. Каждый файл несёт `SaveFormatVersion`; недостающие апгрейды применяются в памяти при чтении, на диск файл переписывается при следующем сохранении. Выпущенные апгрейды не править и не удалять — по ним читаются старые файлы, в том числе скопированные пользователем из резервных копий.
- Изменение раскладки каталога данных, палитр или настроек — новый `IUserDataMigration` с версией на единицу больше последней в конец списка в `Infrastructure/Migrations/UserDataMigrator.cs`. Шаг должен быть повторяемым (может выполниться снова после сбоя); существующие файлы менять через `context.RewriteFile` или предварительный `context.BackUp`. Миграции выполняются в `App.xaml.cs` до загрузки тем и окон; сбой шага не блокирует запуск и повторяется при следующем старте.
- Шаг 1 (`Migration001ImportLegacyExeFolder`) переносит папку `Saves` рядом с exe из версий до 2.0 включительно: списки `*_saves.json` раскладываются по файлам, превью из `SavePrevData` встают рядом, палитры, темы и настройки копируются. Старая папка только читается.
- Проверки и инструменты не трогают настоящие данные: `AppPaths.OverrideDataRoot` перенаправляет каталог (Verification — в `bin/.../VerificationData`, ScreenshotGen — в `bin/.../ScreenshotData`), `RecycleBin.SendOverrideForTests` подменяет Корзину.

Статусы замечаний аудита от 5 октября 2026 — в `FractalExplorerWPF/AUDIT_STATUS.md`. Оба замечания галереи Жюлиа не актуальны после удаления `JuliaGalleryWindow` (`fe82c37`); не переносить их автоматически на карту выбора C.

## Скриншоты окон для документации

`FractalExplorerWPF/ScreenshotGen/` — консольный инструмент, который открывает
каждое WPF-окно приложения по одному (далеко за пределами экрана, невидимо
для пользователя) и сохраняет его как PNG с настоящей рамкой Windows. Он
покрывает буквально весь каталог из «Каталога всех WPF-окон» выше: все пункты
`FractalCatalog.cs`, их «уникальные инструменты» (редакторы палитр,
трансформаций, выбор параметров) и общие служебные окна.

Используй его, когда пользователь просит (пере)сделать скриншоты для README
или аналогичной документации — после заметных визуальных изменений (тема,
раскладка) или после добавления нового окна/фрактала/лаборатории. Не
запускай его по своей инициативе для обычных задач правки кода — это
самостоятельный, не входящий в основное решение инструмент, вызываемый явно:

```powershell
dotnet build .\FractalExplorerWPF\ScreenshotGen\ScreenshotGen.csproj
dotnet run --project .\FractalExplorerWPF\ScreenshotGen\ScreenshotGen.csproj -- .\Pictures\WPF
```

Полный набор охватывает 111 пунктов каталога, редакторы и диалоги и занимает несколько минут; аргумент `smoke` в конце
команды запускает только 4 быстрых скриншота для проверки, что инструмент
работает. Для одного пункта и его редакторов передай `--only=<LaunchKey>`
(например, `--only=Ikeda`); со `smoke` этот фильтр не совмещается.
Устройство инструмента (подмена `Application.ResourceAssembly`,
захват через склейку `PrintWindow`+`RenderTargetBitmap`, ожидание конца
рендера по приватному `_isRendering`) и порядок поддержки при изменениях в
приложении — в `FractalExplorerWPF/ScreenshotGen/README.md`. При добавлении,
удалении или переименовании WPF-окна обновляй заодно и список внутри
инструмента (см. его README), не только таблицы окон в этом файле.

`buddhabrot4d [папка PNG]` — независимая орбита, ограниченная выборка, повороты 4D, шесть GPU-проекций, девять стилей, переиспользование выборки, камера, RGB, тональная коррекция, зонд, кэш, сохранения, облако и WPF-поля;
`shadercache` — повторное использование и инвалидация байткода, восстановление повреждённого файла и пересборка всех 3D-шейдеров, `cloud` — облачные

анонимные GET к настоящему серверу, `poi [фильтр] [--out папка]` — встроенные точки интереса «Комплексной
динамики» не дают однотонный кадр, загружаются в окно без ошибки и дают тот же кадр, что превью (при добавлении или правке точки прогоняй её группу и смотри PNG),
`poi-probe` — рендер кандидатов из JSON без пересборки, `catalog [--out папка]` — главное окно: данные каталога, превью, поиск, разделы, избранное, недавние, привязки и темы (с `--out` — снимки раскладки):
