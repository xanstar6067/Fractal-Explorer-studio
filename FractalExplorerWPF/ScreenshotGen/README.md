# Генератор скриншотов окон WPF

Консольный инструмент, который открывает каждое окно WPF-приложения (по одному
за раз, далеко за пределами экрана — пользователь их не увидит) и сохраняет
его как PNG с настоящей рамкой Windows. Написан для того, чтобы один раз
пересобрать полный набор скриншотов для README/документации без ручного
обхода ~70 окон.

## Когда использовать

- Нужно (пере)сгенерировать скриншоты для README после заметных визуальных
  изменений — новая тема оформления, обновлённая раскладка, новое окно/фрактал/
  лаборатория, новый общий редактор палитры или параметров.
- Нужен быстрый визуальный обзор всех окон приложения (например, перед
  релизом) без открытия каждого вручную.

Инструмент не входит в решение `FractalExplorerWPF.slnx` — собирайте и
запускайте его отдельно.

## Запуск

Из корня репозитория:

```powershell
dotnet build .\FractalExplorerWPF\ScreenshotGen\ScreenshotGen.csproj
dotnet run --project .\FractalExplorerWPF\ScreenshotGen\ScreenshotGen.csproj -- .\Pictures\V2_0_WPF
```

Первый аргумент — папка вывода (создаётся, если её нет; существующие файлы с
такими же именами перезаписываются). Второй необязательный аргумент `smoke`
запускает только 4 быстрых скриншота (каталог, быстрый переключатель, «О
программе», классический Мандельброт) — используйте его, чтобы проверить,
что инструмент вообще работает, прежде чем ждать полный прогон (~70 окон,
несколько минут).

```powershell
dotnet run --project .\FractalExplorerWPF\ScreenshotGen\ScreenshotGen.csproj -- .\Pictures\V2_0_WPF smoke
```

## Как это работает

- **Настоящий `App`, а не голый `Application`.** Просто `new Application()`
  не подключает `Theming/ThemeStyles.xaml` и активную тему — без них не
  находятся стили типа `FractalPanelToggleButtonStyle`, которые использует
  почти каждое окно. Поэтому инструмент создаёт `FractalExplorerWPF.App`,
  вызывает `InitializeComponent()` и `ThemeManager.Initialize(app)` напрямую,
  не вызывая `Run()` — событие `Startup` (которое создало бы реальное
  `MainWindow` и показало его пользователю) так и не срабатывает.
- **Свой каталог данных.** До создания окон вызывается
  `AppPaths.OverrideDataRoot(<bin>/ScreenshotData)`: скриншоты не зависят от
  сохранений, палитр и выбранной темы пользователя в AppData и не пишут туда.
- **Подмена `Application.ResourceAssembly`.** `pack://application:,,,/...`
  по умолчанию резолвится в сборку .exe (`ScreenshotGen`), а превью и другие
  ресурсы зашиты в `FractalExplorerWPF.dll`. Публичный сеттер свойства к
  этому моменту уже недоступен (платформа сама выставляет значение при
  первом обращении), поэтому инструмент подменяет закрытое поле через
  reflection (`ForceResourceAssembly`).
- **Окна открываются далеко за экраном.** `WindowStartupLocation = Manual`,
  `Left`/`Top` — с большим отрицательным смещением, `ShowInTaskbar = false`.
  DWM всё равно выполняет полный layout и рендер, просто ничего не видно на
  реальном мониторе.
- **Захват — склейка PrintWindow и RenderTargetBitmap.** Голый `PrintWindow`
  на окне, стоящем далеко за экраном, отдаёт только рамку и заголовок —
  композитная поверхность WPF-контента там не обновляется и получается
  белой. Поэтому рамка/заголовок берутся через `PrintWindow`
  (`PW_RENDERFULLCONTENT`), а содержимое клиентской области — надёжным
  `RenderTargetBitmap` (он всегда корректно рендерит визуальное дерево
  независимо от положения окна на экране), и оба изображения склеиваются в
  одно по смещению `ClientToScreen`.
- **Ожидание конца рендера.** Многие окна выставляют приватное поле
  `_isRendering` на время расчёта кадра (частый паттерн в проекте). Фиксированной
  паузы не всегда достаточно — например, Nova Mandelbrot мог сняться раньше,
  чем движок закончил кадр. `WaitForRenderIdleAsync` через reflection ждёт,
  пока флаг не станет `false` (с разумным пределом на случай окон без такого
  поля или с непрерывной симуляцией — Gray–Scott, DLA, Flame, Буддаброт).
- **«Уникальные инструменты» каждого окна** (редакторы палитр, редакторы
  трансформаций, выбор параметров) открываются либо прямым конструированием с
  аргументами, добытыми через reflection из приватных полей уже открытого
  окна (`_paletteManager`, `_transforms` и т.п.), либо, для окон с приватным
  конструктором и статическим модальным `Open(...)` (`SaveManagerWindow`,
  `ImageExportManagerWindow`), — через `CaptureModalAsync`: до вызова
  модального метода в очередь диспетчера кладётся задача, которая находит
  новое окно в `Application.Current.Windows`, ждёт, снимает скриншот и сама
  его закрывает, позволяя `ShowDialog()` вернуться.

## Поддержка при изменениях в приложении

Все восемь режимов `BasinExplorerWindow` входят через ключи `Basins:` каталога, включая
комплексную логистическую карту, магнитный маятник и систему притягивающих центров.
Редактор физических центров встроен в основное окно; отдельного диалога нет.
Физические модели по умолчанию используют быстрый предпросмотр в треть разрешения;
ожидание `_isRendering` применяется к ним так же, как к остальным бассейнам.

Список окон и их «уникальных инструментов» — это набор `case`-веток в
`ProcessCatalogItemAsync` (для пунктов каталога, `Models/FractalCatalog.cs`)
плюс несколько прямых вызовов в начале `RunAllAsync` (общие служебные окна).
При добавлении, удалении или переименовании WPF-окна, каталожного пункта или
общего диалога — обновите соответствующую ветку здесь так же, как обновляете
таблицы окон в `CLAUDE.md`/`AGENTS.md`. Если у нового окна есть кнопка,
открывающая ещё одно окно (палитра, редактор параметров), которое стоит
попадания в скриншоты, — добыть нужные аргументы конструктора можно через
`GetMember(parentWindow, "_названиеПоля")` по образцу уже существующих веток.
