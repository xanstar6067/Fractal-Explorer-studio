# Протокол FractalCloud

Справочник по сетевому протоколу, который использует WPF-клиент (`Infrastructure/Cloud/`) для общения с сервером FractalCloud. Нужен, если вы поднимаете свою совместимую реализацию сервера или пишете альтернативного клиента. Описывает только формат запросов/ответов и его смысловые правила — конкретный адрес, учётные данные и инфраструктура развёртывания сюда не входят (см. `CLOUD.md`, раздел «Безопасность подключения», про `cloud-connection.local.json`).

Контракт извлечён из фактического поведения клиента (`FractalCloudClient.cs`, `CloudConnection.cs`, `Models/CloudModels.cs`) — он не переопределён с нуля и не должен расходиться с этими файлами. При любом расхождении между этим документом и кодом ориентир — код.

## 1. Транспорт

- Только HTTPS. Адрес сервера — `https://host:port` без пути, query и userinfo (клиент отклоняет остальные формы, см. `CloudConnection.GetServerUri`).
- Автоматические HTTP-редиректы клиент не выполняет (`AllowAutoRedirect = false`) — сервер не должен на них полагаться.
- Тело запросов и ответов — JSON, `Content-Type: application/json`, кодировка UTF-8.
- Таймаут запроса на стороне клиента — 60 секунд, установления соединения — 15 секунд.

### TLS-сертификат

Приложение не отключает и не подменяет проверку TLS. Есть два поддерживаемых варианта:

1. **Публичный сертификат** (Let's Encrypt или другой доверенный ЦС) — работает без дополнительной настройки, проверка идёт через системное доверие Windows.
2. **Частный корневой ЦС** (например, локальный ЦС Caddy) — его публичный сертификат нужно встроить в клиент отдельным файлом и явно подключить как `CustomRootTrust` (`SslClientAuthenticationOptions.CertificateChainPolicy`). Приватные ключи сервера в клиент никогда не попадают. Для частного ЦС без CRL/OCSP проверка отзыва сертификата не выполняется (`X509RevocationMode.NoCheck`), но имя сервера, цепочка, назначение (`serverAuth`, OID `1.3.6.1.5.5.7.3.1`) и сроки действия проверяются всегда.

Реализация с обработчиком, принимающим любой сертификат (`ServerCertificateCustomValidationCallback => true` или аналог), протоколу не соответствует.

## 2. Аутентификация

Аутентификация — по паре access/refresh токенов (Bearer). Регистрация пользователей в протокол не входит — предполагается, что учётная запись создана заранее на сервере.

### `POST /auth/login`

Запрос:

```json
{
  "email": "user@example.com",
  "password": "секрет"
}
```

Ответ `200 OK`:

```json
{
  "tokenType": "Bearer",
  "accessToken": "...",
  "expiresIn": 3600,
  "refreshToken": "..."
}
```

Требования к ответу, которые проверяет клиент (иначе он считает ответ сервера некорректным и обрывает вход):

- `tokenType` — точно `"Bearer"` (без учёта регистра).
- `accessToken` и `refreshToken` — непустые строки.
- `expiresIn` — целое число секунд, строго больше `0` и не больше `31 536 000` (365 дней).

Неверные email/пароль — `401 Unauthorized`.

### `POST /auth/refresh`

Запрос:

```json
{ "refreshToken": "текущий refresh token" }
```

Ответ — тот же формат, что у `/auth/login`, с теми же требованиями. Сервер должен выдать новую пару токенов; клиент полностью заменяет обе локально хранимые строки значениями из ответа и никогда не переиспользует старый refresh token повторно.

Любая ошибка (`401`, сетевой сбой, некорректный ответ) означает, что refresh token больше не годится: клиент считает сеанс завершённым и требует новый `/auth/login`.

### Авторизация защищённых запросов

```
Authorization: Bearer <accessToken>
```

Сервер должен возвращать `401 Unauthorized` на отсутствующий, просроченный или отозванный access token — и ни на что другое, чтобы не запускать у клиента лишний refresh-цикл.

### Поведение клиента, которое должен выдерживать сервер

- Перед каждым запросом клиент сверяет `expiresIn` (с запасом ≈10%, но не больше 30 секунд) и обновляет токен заранее, не дожидаясь `401`.
- Если запрос всё же получил `401`, клиент выполняет ровно одну попытку `/auth/refresh` и один повтор исходного запроса с новым access token. Второй `401` подряд — сеанс закрывается на стороне клиента без дальнейших попыток.
- Все обращения к `/auth/*` и `/api/*` в клиенте сериализованы одним семафором: параллельных `/auth/refresh` для одного клиента быть не может. Сервер всё равно должен переживать параллельные refresh-запросы от разных экземпляров клиента (например, если пользователь работает на двух ПК) — это штатная ситуация, а не гонка, которую нужно предотвращать 409.
- Endpoint отзыва токенов (logout) в протокол не входит: «выход» — чисто локальная операция клиента (стирание сохранённого refresh token), без обращения к серверу.

## 3. Сохранения (`/api/saves`)

Все запросы этого раздела требуют заголовок `Authorization`. Сохранение принадлежит пользователю, чей access token использован; чужие ID должны выглядеть как `404`, а не как `403`, чтобы не подтверждать факт существования чужой записи.

### Модель сохранения

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "name": "Название",
  "revision": 1,
  "createdAt": "2026-01-01T12:00:00Z",
  "updatedAt": "2026-01-01T12:00:00Z",
  "jsonData": "{...}"
}
```

- `id` — GUID, назначается сервером при создании.
- `name` — строка длиной 1–100 символов (UTF-16 code units).
- `revision` — счётчик версий, начинается с `1`, увеличивается на каждое успешное `PUT`.
- `createdAt` / `updatedAt` — ISO 8601 с указанием часового пояса (клиент разбирает как `DateTimeOffset`).
- `jsonData` — **строка**, содержащая сериализованный JSON-объект (двойное кодирование: JSON внутри JSON-строки, с экранированием кавычек). Сервер не обязан понимать содержимое `jsonData` — это непрозрачный payload клиента (см. раздел 5) — но обязан проверить, что это синтаксически корректный JSON, и хранить его как есть, включая порядок и форматирование.

### `GET /api/saves`

Список сохранений текущего пользователя. Ответ — JSON-массив объектов сохранения **без поля `jsonData`** (только метаданные — иначе список с большим числом сохранений стал бы неприемлемо тяжёлым). Порядок не специфицирован клиентом.

```json
[
  { "id": "...", "name": "...", "revision": 1, "createdAt": "...", "updatedAt": "..." }
]
```

### `GET /api/saves/{id}`

Одно сохранение вместе с `jsonData`. `404`, если ID не существует или принадлежит другому пользователю.

### `POST /api/saves`

Запрос:

```json
{ "name": "Название", "jsonData": "{\"zoom\":1000}" }
```

Сервер создаёт запись, назначает `id` и `revision = 1`. Ответ — полный объект сохранения (`201`/`200` с телом; конкретный код клиент не проверяет, только `IsSuccessStatusCode`).

Количество сохранений на пользователя протоколом не ограничивается.

Идемпотентности у `POST` нет: если соединение оборвалось после того, как сервер принял запрос, но до того, как ответ дошёл до клиента, повторная отправка того же имени создаст вторую запись. Клиентам следует обрабатывать это на своей стороне (например, обновлением списка перед повтором), а не ждать этого от сервера.

### `PUT /api/saves/{id}`

Запрос:

```json
{ "name": "Новое название", "jsonData": "{\"zoom\":2000}", "revision": 1 }
```

`revision` — версия, которую клиент считает текущей (оптимистичная блокировка). Правила сервера:

- Если `revision` совпадает с текущей версией записи — применить изменения, увеличить `revision` на 1, обновить `updatedAt`, вернуть полный объект сохранения.
- Если `revision` меньше текущей — запись изменена кем-то ещё, вернуть `409 Conflict`:

  ```json
  { "message": "Save was modified.", "currentRevision": 2 }
  ```

  Клиент обязан показать выбор пользователю (перечитать актуальную версию, слить вручную), а не просто повторить `PUT` с новой `revision` вслепую — сервер этого не проверяет и не обязан защищать от такого клиентского поведения, но собственная реализация клиента должна.

### `DELETE /api/saves/{id}?revision={revision}`

`revision` в query — та же оптимистичная блокировка, что у `PUT`: несовпадение — `409` с тем же форматом тела, что и выше. Успех — `204 No Content`, без тела.

Здесь нет «мягкого» удаления на уровне протокола: получив `204`, клиент должен считать запись окончательно удалённой на сервере. Как реализовать это в БД сервера (жёсткое или мягкое удаление) — решение конкретной реализации сервера, протокол этого не специфицирует; важно только, чтобы `GET`/`PUT`/`DELETE` по удалённому `id` дальше возвращали `404`, а не «успех».

## 4. Ограничения и коды ошибок

| Ограничение | Значение |
|---|---|
| Длина `name` | 1–100 символов |
| Размер `jsonData` | ≤ 1 МиБ (1 048 576 байт) в UTF-8, считая экранирование |
| Число сохранений на пользователя | не ограничено |

| Код | Когда возвращает сервер | Как трактует клиент |
|---|---|---|
| `200` | Успешный `GET`/`POST`/`PUT` | Тело — JSON по схеме раздела 3 |
| `204` | Успешный `DELETE` | Без тела |
| `400` | `name`/`jsonData` не проходят валидацию или `jsonData` — не корректный JSON | Ошибка данных, повтор без исправления бессмысленен |
| `401` | Access token отсутствует, просрочен или недействителен | Один refresh + один повтор запроса (раздел 2) |
| `404` | Сохранение не существует либо принадлежит другому пользователю | Разница между этими двумя случаями клиенту не сообщается |
| `409` | `PUT`/`DELETE` с устаревшей `revision` | Тело — `{ "message": "...", "currentRevision": N }`; конфликт разрешает пользователь |
| `413` | Тело запроса превышает лимит на уровне HTTP/веб-сервера | То же, что `400` по сути, отдельное сообщение для пользователя |

Ответы на `/auth/login` и `/auth/refresh` могут содержать секреты — клиентские реализации не должны логировать тело этих ответов (и тело запроса с паролем) ни при успехе, ни при ошибке.

## 5. Формат `jsonData` конкретно у WPF-клиента

Это соглашение конкретного клиента, а не часть серверного протокола — сервер хранит `jsonData` непрозрачно. Приведено для совместимости, если вы пишете свой клиент и хотите читать/писать сохранения, совместимые с WPF-версией:

```json
{
  "format": "FractalExplorerWPF",
  "version": 1,
  "category": "Mandelbrot",
  "state": { "...": "обычные поля JSON-сохранения этого режима, включая SaveFormatVersion" }
}
```

`category` соответствует подкаталогу в `Saves/<режим>/` локального хранилища (см. `CLOUD.md`). Свой клиент может использовать произвольный `format`, но тогда WPF-версия будет показывать такие записи как «не поддерживается» (см. `CloudEntryState.Unsupported`) — это ожидаемо и не является ошибкой протокола.

## 6. Обязанности реализации клиента (сводка)

Чтобы совместимый клиент вёл себя не хуже эталонного:

1. Пароль нигде не сохраняется (ни на диск, ни в конфиг) — вводится заново при каждом полном входе.
2. Access token — только в памяти процесса.
3. Refresh token — в защищённом хранилище ОС (на Windows — DPAPI или Credential Manager, не обычный файл настроек в открытом виде).
4. Перед запросом — проверка `expiresIn` с упреждающим обновлением; на `401` — один refresh и один повтор, без бесконечных циклов.
5. Не запускать два параллельных `/auth/refresh` для одного и того же refresh token — сериализовать через блокировку/семафор.
6. Неуспешный refresh — удалить оба локальных токена и заново запросить email/пароль у пользователя.
7. Ни пароль, ни токены не должны попадать в логи или тексты исключений, показываемые пользователю.
8. `409` при `PUT`/`DELETE` — не перезаписывать молча; подтягивать актуальную версию и явно решать конфликт (вручную или по понятной стратегии слияния).
